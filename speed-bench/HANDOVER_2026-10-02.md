- **GLM budgeted streaming is structurally unsupported for GLM-5.3-Flash-Q2 on
  Metal.** Its routed layers are IQ2_XXS gate/up with Q2_K down and use 8 experts.
  Every GLM expert-cache predicate rejects that on Apple:
  `glm_stream_selected_expert_cache_supported` requires
  `DS4_N_EXPERT_USED == 6` for IQ2/Q2_K under `__APPLE__` (`ds4.c:8369-8373`,
  "Metal's IQ2/Q2 selected-slot down kernel sums six experts"), and the seeder
  gate at `ds4.c:22636-22646` has the same `== 6`. No layer is "streamed", so:
  - static map on (default): the map is the whole file (89.88 GiB) whatever
    `--ssd-streaming-full-layers` is set to, so it can never fit a ~70 GiB
    budget. Lever (b) is dead.
  - static map off (or a tighter `DS4_GLM_MEMORY_GUARD_RESERVE_GB`): per-layer
    fallback maps each layer's full expert span from the mmap every token. The
    58 GiB cache is budgeted but never populated.
  - preload: the seeder returns before printing anything (no layer qualifies),
    and there is no built-in hotlist for GLM53 (PRO, FLASH and GLM52 only,
    `ds4.c:22919-22930`).
  - lever (c) `--simulate-used-memory` cannot change the plan: the budget reads
    `hw.memsize`.
- **Probe A measured** (`m3_max_glm53f_q2_1003_A_nostatic_preload.*`, killed
  after one frontier): static map off, 62 GB cache, preload 8829. **73.26 GiB
  planned, ~14 GiB wired, 2K reading 161.7 t/s, writing 0.58 t/s.** In budget but
  useless; worse than the earlier cold 1.09 t/s.
- **Routes forward** (both need code or a new GGUF): an 8-expert IQ2-gate /
  Q2_K-down selected-slot Metal kernel, relaxing the `== 6` guards (8372, 22641,
  ~20078); or requantising to a supported layout (uniform Q2_K, or IQ2_XXS
  down). Either also needs a GLM53 hotlist for preload.
  ROCm lacks the Apple-only `== 6`, so it probably works there (inferred, not
  tested).
- **For the upstream report (item 3)**, the third point is now sharper. On
  Metal, GLM 5.3 Q2 has no budgeted mode at all. The default static map ignores
  the budget, and the budget-honouring fallback leaves the requested cache
  empty. Worth asking whether the `== 6` kernel limit is known for GLM 5.3,
  which uses 8.
- **Upstream PR search (2026-10-03):** nothing fixes this layout. The closest is
  #1172 / issue #1171, "cache GLM mixed Q2/Q4 routed experts", opened
  2026-10-02 and still unmerged. It covers **Q2_K gate/up with Q4_K down** (it
  widens the addr-layout predicate), not IQ2_XXS gate/up with Q2_K down and 8

## Conventions

- **Quote pass 2.** Pass 1 brings the machine to its sustained operating point
  and carries cache-churn dips that move between runs (16K–20K on one, 20K–26K
  on another). Figures published before 2026-10-02 were the *mean* of both
  passes — the method section claimed pass 2, so the tables and the text
  disagreed. Now corrected to pass 2 throughout `M3_MAX_DS4_VS_GLM.md`.
- **`gen_steady_tps`, not `gen_tps`.** The latter averages in the first-token
  wait, which is ~40 ms resident but ~1,300 ms streamed, so it conflates two
  very different quantities.
- Every run records the resident app load at launch in
  `m3_max_1002_queue.log`; memory is sampled every 15 s by `memsample.sh`.

## What was established

1. **DeepSeek streams well at a 70 GiB budget.** −32% reading, −12% writing
   (mean 16K–32K), and first token goes 42 ms → 1,311 ms (31×). The writing
   penalty shrinks to −5% by 32K. Written up in `docs/M3_MAX_STREAMING.md`.
2. **GLM ignores the budget.** Asked for 62 GiB it maps all 89.87 GiB as a
   global static decode map, shrinks the cache to 9 GiB, and plans 106 GiB —
   more than running resident. Cause: the fit check in `ds4.c:68440-68465` tests
   *total* RAM, and `metal_graph_stream_decode_static_map_enabled()`
   (`ds4.c:19739`) returns `true` unconditionally on Metal.
3. **The current build is faster than the published baseline** by 6% reading and
   10% writing (resident, mean 16K–32K). Confounded between the 11 hot-path
   commits and the OS upgrade — not attributed. Separable by building `6289c51`
   and re-running resident on today's OS.
4. **DeepSeek's lead over GLM is larger than published**: 17–48% reading and
   12–30% writing over 2K–64K, against the published 10–27%.
5. **Running with VMs up costs little.** 38 GiB of apps vs 24 GiB: −6% reading,
   −4% writing, +22% first token. But starting a model compresses whatever else
   is resident — two VMs went 31 GiB → 3 GiB within a minute.
6. **The September power fault did not reproduce.** Three attempts, 65 W and
   140 W adapters, 24 GiB and 38 GiB app loads: all clean. See
   `~/Desktop/m3-max-reset-report/` and the memory note `m3-max-uvlo-resets`.
   The `ResetCounter` diag remains the only hard evidence; keep the Apple
   appointment.

### 3. Upstream report (if (2) fails)

The user intends to submit this. It is a strong report because the behaviour is
pure upstream code — `ds4_ssd.c` and the static-map decision are identical on
`antirez/main`, so it reproduces there with no fork patches involved. The two
questions worth asking:

- Should the static-map fit check consider free memory rather than total? As it
  stands, a 128 GiB machine with 54 GiB of apps commits to a 106 GiB plan the
  kernel then cannot keep wired — wired memory flaps 24↔97 GiB for the whole
  run, swap is touched, and other applications are compressed out.
- Should an explicit `--ssd-streaming-cache-experts` ever be silently overridden?
  62 GiB became 9 GiB with only a line on stderr. Refusing, or sizing the map to
  what will stay wired, both seem better than quietly delivering the opposite of
  what was asked.

Reproduce with: `./ds4 -m gguf/GLM-5.3-Flash-Q2.gguf --ssd-streaming
--ssd-streaming-cache-experts 62GB --ctx 32768` and read the startup plan.

### 4. MTP: no regression, but the page was misleading (now fixed)

Investigated and closed. Tonight's full-sweep figure, GLM `--mtp` at 9.8 t/s
against plain decode's 15.9 (32 frontiers, pass 2, −38%), reproduces the
published full-sweep sentence (9.4 vs 14.9, −37%) to within 4%. **There is no
regression.**

What looked like one: the page led with **−13%**, which was the mean over four
short frontiers (2K–8K), while its own text gave −37% for the full range. The
per-frontier spread tonight was −8% to −53%, so a four-frontier window can land
almost anywhere. `M3_MAX_GLM_MTP.md` now leads with the full-sweep figure and
says plainly that any single percentage summarises a wide distribution.

Also worth knowing: the margin ordering does not reproduce. Published had
default best (−13%) and margin 1 worst (−43%); tonight all three sit within
three points (−31%, −29%, −29%) with default marginally *worst*. The doc's
own caveat — that only "all three lose" is robust — held up, and is now
strengthened to say the ordering has already changed between runs.
